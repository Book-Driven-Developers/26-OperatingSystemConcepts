# Chapter 10 가상 메모리 

가상 메모리 : 실행하고자 하는 프로그램을 일부만 메모리에 적재하여 실제 물리 메모리 크기보다 더 큰 프로세스를 실행할 수 있게 하는 기술

프로그램을 일부만 메모리에 올려놓고 실행했을 때 가질 수 있는 이점
1. 프로그램이 물리 메모리 크기에 제약받지 않는다. 
2. 더 많은 프로그램을 동시에 수행할 수 있어, 응답 시간을 유지하면서도 CPU 이용률과 처리율이 높아진다. 
3. 프로그램을 메모리에 올리고 스왑하는 I/O 횟수가 줄어든다. 
4. 메모리 사용량 감소

## Demand Paging
(페이지가 없을 때, OS가 어떻게 처리할까.)

- 페이지가 실제로 필요해지는 시점에 해당 페이지를 메모리에 적재하는 방식 (lazy loading)

페이지가 메모리에 있는지 valid/invalid bit를 통해서 알 수 있다. 
- valid : 해당 페이지가 정상적으로 물리 메모리에 존재한다. 
- invalid -> 하드웨어가 OS로 page fault trap을 발생시킨다. 
  - 프로세스의 주소가 유효하지 않음 (가상 주소 공간상에 정의되지 않음)
  - 유효한 페이지지만 현재 물리 메모리에 없음

#### page fault 처리 과정 
1. 페이지 테이블 확인
	- CPU가 페이지에 접근했을 때 페이지 테이블의 valid/invalid bit 확인
	- 해당 페이지가 invalid 상태라면 운영체제로 trap 발생
2. 메모리 접근의 유효성 검사
	- 운영체제는 해당 주소가 프로세스의 유효한 주소인지 확인
	- 잘못된 주소에 대한 접근이라면 프로세스를 종료
	- 유효한 주소지만 페이지가 메모리에 없는 경우 페이지를 적재
3. 빈 프레임(Free Frame) 확보
	- 필요한 페이지를 적재할 물리 메모리의 빈 프레임을 찾는다
	- 빈 프레임이 없다면 페이지 교체 필요
4. 페이지를 메모리로 적재
	- 보조 저장장치에 존재하는 페이지를 읽어 확보한 프레임에 적재
	- 디스크 I/O가 발생하기 때문에 페이지 폴트 처리 과정에서 가장 큰 비용이 발생한다.
5. 페이지 테이블 갱신
	- 페이지가 적재된 프레임 번호를 페이지 테이블에 기록하고 해당 페이지를 valid 상태로 변경
6. 중단된 명령어 재실행
	- 페이지 폴트를 발생시킨 명령어를 다시 실행

- 이제 필요한 페이지가 메모리에 존재하므로 정상적으로 메모리에 접근할 수 있다.

### Pure Demand Paging
- 프로세스를 시작할 때, 페이지를 미리 메모리에 적재하지 않고, 실제로 페이지가 참조되는 순간에만 메모리에 적재한는 방식
  
- 페이지 테이블
  - 페이지가 현재 물리 메모리에 존재하는지 확인할 수 있다.
  - 일반적으로 valid/invalid bit 등의 정보를 이용
- 보조 저장장치 
  - 현재 물리 메모리에 존재하지 않는 페이지를 저장할 공간
  - 페이지 폴트가 발생하면 필요한 페이지를 이곳에서 물리 메모리로 가져온다.

### demanding page 성능
demand paging 에서는 페이지 폴트 발생 빈도가 전체 시스템 성능에 큰 영향을 주는데, 페이지 폴트가 발생하면 운영체제로 제어권이 넘어가고 필요한 페이지를 보조 저장장치에서 읽어와야 하기 때문이다. 

page fault시에 필요한 추가 작업
- 운영체제로 trap
- 메모리 접근의 유효성 검사
- 빈 프레임 확보
- 보조 저장장치에서 페이지 읽기 (일반적인 메모리 접근보다 더 느림!)
- 페이지 테이블 갱신
- 중단된 명령어 재실행

## Copy-On-Write

Copy-on-Write(COW)는 처음에는 부모와 자식이 동일한 물리 페이지를 공유하고, 둘 중 하나가 해당 페이지를 수정하려고 할 때 실제 복사본을 만드는 방식이다.

fork()시 부모 프로세스의 모든 메모리를 즉시 복사하지 않고 부모와 자식이 물리 페이지를 공유하도록 함으로써 fork()의 비용과 메모리 사용량을 줄일 수 있다.

공유 페이지에 쓰기가 발생하면 해당 페이지가 read-only이므로 Page Fault가 발생하면서 운영체제로 제어권이 넘어가고, 운영체제는 새로운 프레임을 할당하여 기존 페이지를 복사한 뒤 해당 프로세스의 페이지 테이블을 변경한다. 이후 새 페이지에 쓰기가 가능하도록 권한을 변경하고, 쓰기를 시도했던 명령어를 다시 실행한다.

- 장점 : 불필요한 메모리 복사를 줄일 수 있다.


## Page Replacement
프로세스들이 계속 실행되다 보면 물리 메모리의 모든 프레임이 사용중인 상황이 발생할 수 있다. 이때 새로운 페이지를 메모리에 적재하려면 현재 메모리에 존재하는 페이지 중 하나를 제거하여 프레임을 확보해야 한다.

#### 페이지 교체 과정
1. 메모리에 존재하는 페이지 중 제거할 페이지 선택
2. 희생 페이지가 수정된 페이지라면 보조 저장장치에 내용을 기록
3. 희생 페이지가 사용하던 프레임을 해제
4. 필요한 페이지를 해당 프레임에 적재
5. 관련 페이지 테이블을 갱신
6. 페이지 폴트를 발생시킨 명령어를 다시 실행


### 페이지 교체 알고리즘
앞으로 다시 사용될 가능성이 낮은 페이지를 선택하여 page fault 발생률을 최소화하자. 
좋은 알고리즘일수록 Page Fault 발생 횟수를 줄일 수 있다.

#### FIFO (First-In-First-Out)
- 메모리에 가장 먼저 들어온 페이지를 가장 먼저 교체하는 방식
구현이 간단하지만 실제 사용 빈도를 고려하지 않으며, 프레임 수를 늘렸는데 오히려 Page Fault가 증가하는 Belady's Anomaly가 발생할 수 있다.

#### Optimal Page Replacement (OPT)
- 앞으로 가장 오랫동안 사용되지 않을 페이지를 교체
이론적으로 가장 낮은 Page Fault를 보장하지만 미래의 메모리 접근을 알아야 하므로 실제로 구현할 수 없으며 다른 알고리즘의 성능 비교 기준으로 사용된다.

#### LRU (Least Recently Used)
- 가장 오랫동안 사용되지 않은 페이지를 교체하는 방식
최근에 사용된 페이지는 가까운 미래에도 사용될 가능성이 높다는 지역성(Locality)을 이용하며 성능은 좋지만, 정확한 최근 사용 순서를 관리하는 비용이 발생한다.

페이지마다 마지막 사용시간을 유지하여 이 값을 사용한다. 
- 계수기 : 가장 간단한 방법으로, 페이지마다 사용 시간 필드를 넣고 CPU에 논리적인 시계나 계수기를 추가한다. 
- 스택 : 페이지 번호의 스택을 유지하면 스택의 꼭대기는 항상 최근에 사용된 페이지고 밑바닥은 가장 오랫동안 사용되지 않은 페이지다. 


#### LRU Approximation
- 정확한 LRU 구현 비용을 줄이기 위해 Reference Bit를 이용해 LRU를 근사하는 방식
정확한 LRU는 모든 페이지의 최근 사용 순서를 추적해야 하므로 구현 비용이 크다. 이를 줄이기 위해 하드웨어가 제공하는 Reference Bit(R bit)를 이용해 LRU를 근사한다.

1. Additional-Reference-Bits Algorithm
각 페이지에 여러 개의 Reference Bit를 추가하여 일정 주기마다 사용 기록을 오른쪽으로 Shift한다.
최근에 많이 참조된 페이지일수록 큰 값을 가지므로, 가장 작은 값을 가진 페이지를 교체하여 LRU를 근사한다.

2. Second-Chance Algorithm
FIFO를 기반으로 하되 페이지의 Reference Bit가 1이면 즉시 교체하지 않고 R=0으로 만든 뒤 한 번 더 기회를 준다. R=0인 페이지가 발견되면 교체하며, 최근 사용된 페이지가 FIFO만으로 제거되는 문제를 보완한다.

3. Enhanced Second-Chance Algorithm
Reference Bit뿐 아니라 Modify(Dirty) Bit까지 함께 사용하여 (R, M) 조합으로 교체 우선순위를 결정한다.
(0,0) → (0,1) → (1,0) → (1,1) 순으로 선호하며, 최근 사용되지 않았고 수정도 안 된 페이지를 가장 먼저 교체한다.

### Counting-Based Page Replacement
각 페이지가 얼마나 많이 참조되었는지를 Counter로 기록하고 이 값을 기준으로 Victim을 결정한다.

- LFU(Least Frequently Used): 참조 횟수가 가장 적은 페이지를 교체한다. 자주 사용된 페이지는 앞으로도 사용할 가능성이 높다고 가정한다.
- MFU(Most Frequently Used): 참조 횟수가 가장 많은 페이지를 교체한다. 참조 횟수가 적은 페이지는 최근에 들어와 아직 충분히 사용되지 않았다고 가정한다.

다만 LFU와 MFU 모두 일반적인 LRU 근사보다 성능이 좋지 않아 널리 사용되지는 않는다.

### Page-Buffering Algorithm
페이지 교체 시 바로 프레임을 재사용하는 것만이 아니라, 일정 수의 가용 프레임을 미리 확보해 두어 Page Fault 발생 시 즉시 페이지를 적재할 수 있도록 하는 방식이다.

교체된 페이지도 잠시 보존해두었다가 다시 필요해지면 디스크에서 읽지 않고 복구할 수 있으며, Dirty Page의 디스크 쓰기도 별도로 처리하여 Page Fault 처리 시간을 줄이는 데 목적이 있다.

## 프레임 할당
여러 프로세스가 동시에 실행되면 운영체제는 사용 가능한 물리 메모리의 프레임을 각 프로세스에 분배해야 한다.

프로세스가 너무 적은 프레임을 받으면 Page Fault가 빈번하게 발생하고, 반대로 특정 프로세스가 너무 많은 프레임을 사용하면 다른 프로세스가 사용할 메모리가 부족해진다.

따라서 운영체제는 각 프로세스에 몇 개의 프레임을 할당할 것인지, 그리고 Page Replacement가 필요할 때 어느 범위에서 Victim을 선택할 것인지 결정해야 한다.

### 최소 프레임 수 
각 프로세스에는 정상적으로 명령어를 실행하기 위해 필요한 최소한의 프레임 수가 존재한다.

최소 프레임 수는 CPU 아키텍처의 Instruction Set Architecture(ISA)에 의해 결정되며, 하나의 명령어가 동시에 참조할 수 있는 페이지 수 등이 영향을 준다.
	- 예를 들어 하나의 명령어가 명령어 자체와 여러 개의 메모리 operand를 참조한다면 이들을 처리할 수 있을 만큼의 프레임이 필요하다.

최대 프레임 수는 시스템에서 사용 가능한 전체 물리 프레임 수에 의해 제한된다.

### 할당 알고리즘
가장 단순한 방법은 균등 할당(Equal Allocation)으로, 사용 가능한 프레임을 모든 프로세스에 동일하게 나누는 방식이다.

하지만 프로세스마다 필요한 메모리 크기가 다르므로 비례 할당(Proportional Allocation)을 사용할 수도 있다. 프로세스의 크기가 클수록 더 많은 프레임을 할당한다.

또한 프로세스의 우선순위를 고려하여 Priority Allocation을 적용할 수도 있다.

모든 프로세스에 똑같이 줄 것인지, 프로세스의 크기나 중요도를 고려해서 다르게 줄 것인지.

### 전역 대 지역 할당 (Global versus Local Allocation)

Global Replacement는 다른 프로세스가 사용하는 프레임까지 Victim으로 선택할 수 있어 전체 메모리를 유연하게 활용할 수 있지만, 한 프로세스의 동작이 다른 프로세스의 Page Fault율에 영향을 줄 수 있다.

Local Replacement는 자신에게 할당된 프레임 안에서만 Victim을 선택하므로 프로세스 간 영향이 적고 성능을 예측하기 쉽지만, 남는 프레임을 유연하게 활용하기 어렵다.

결국 Global은 시스템 전체 효율성, Local은 프로세스 간 격리와 예측 가능성 측면에서 장단점이 있다.

### Non Uniform Memory Access
멀티프로세서 시스템에서는 CPU와 메모리 사이의 접근 시간이 항상 동일하지 않을 수 있다.
특히 여러 CPU Socket을 사용하는 서버에서는 각각의 CPU가 자신과 가까운 메모리를 가지고 있는 구조가 사용되는데 이를 NUMA(Non-Uniform Memory Access)라고 한다. 이때 CPU가 Local Memory에 접근하는 것과 Remote Memory에 접근하는 것의 비용이 달라진다. 

NUMA 시스템에서는 단순히 “빈 프레임이 어디 있는가?”만 보고 메모리를 할당하면 성능이 떨어질 수 있다.
예를 들어 CPU 0에서 실행되는 프로세스의 페이지를 Node 1의 메모리에 계속 할당하면 CPU 0은 데이터를 읽을 때마다 Remote Memory Access를 해야 한다.
따라서 운영체제는 가능하면 프로세스가 실행되는 CPU와 가까운 NUMA Node의 물리 프레임을 할당하여 메모리 접근 지연 시간을 줄여야 한다. 

> NUMA 시스템에서는 CPU Scheduling과 Memory Allocation을 완전히 독립적으로 생각하기 어렵다. + NUMA locality <
- first touch 
```
Thread 0 (Node 0) -> 큰 메모리 영역 초기화 -> 대부분의 Physical Page가 Node 0에 할당

이후 node 1에 해당 프로세스를 고정시킴 

Thread 1 (Node 1) -> 그 메모리를 계속 사용 -> Remote Memory Access 증가
```

## Thrashing
프로세스에 필요한 프레임이 충분히 할당되지 않아서 page fault가 지나치게 자주 발생하고, cpu가 실제 작업보다 페이지를 교체하는데 대부분의 시간을 사용하는 현상
-> 시스템 처리량과 cpu 사용률이 감소한다. 

### 스레싱의 원인

메모리 부족 -> Page Fault 증가 -> 프로세스들이 I/O 대기 -> CPU 이용률 감소 -> OS가 프로세스를 더 추가 -> 프로세스당 Frame 감소 -> Page Fault 더욱 증가 -> Thrashing

각 프로세스가 실제로 필요로 하는 만큼의 프레임을 확보할 수 있도록 해야 한다.

### Working-set 모델
- 최근에 이 프로세스가 실제로 사용하는 페이지가 몇 개인지 보고 그만큼의 프레임을 주자.

프로그램은 지역성(Locality)을 가지므로 특정 시간 동안 모든 페이지를 골고루 사용하는 것이 아니라 일부 페이지를 집중적으로 사용한다.
이때 최근 일정 시간 동안 프로세스가 실제로 참조한 페이지들의 집합을 Working Set이라고 한다.
Working Set의 크기는 해당 시점에서 프로세스가 원활하게 실행되기 위해 필요한 프레임 수를 근사한다고 볼 수 있다.
운영체제는 각 프로세스의 Working Set 크기를 계산하고 그만큼의 프레임을 제공하려고 한다.
전체 프로세스의 Working Set 크기를 합한 값이 사용 가능한 전체 프레임보다 크다면 시스템이 모든 프로세스의 요구를 만족시킬 수 없다는 뜻이고, thrashing이 발생할 확률이 높다. 

이 경우 일부 프로세스를 중단하거나 swap out하여 Degree of Multiprogramming을 낮춰야 한다.

### page fault frequency
- page fault가 얼마나 발생했는지 확인하여 fage fault rate에 상한과 하한을 정해주자.

Working Set은 어떤 페이지들이 사용되고 있는지 직접 추적해야 하므로 관리 비용이 발생한다. 보다 직접적인 방법으로 Page-Fault Frequency, PFF 자체를 감시할 수 있다. 

Page Fault율이 너무 높다면
- 해당 프로세스가 프레임이 부족하다고 판단
- 더 많은 프레임을 할당한다.

Page Fault율이 너무 낮다면
- 필요 이상으로 많은 프레임을 가지고 있다고 판단
- 일부 프레임을 회수한다.

만약 Page Fault율이 높은데도 추가로 제공할 프레임이 없다면 일부 프로세스를 중단하여 프레임을 확보할 수 있다. 

## 메모리 압축
메모리가 부족할 때, 일부 페이지를 압축해서 RAM에 그대로 유지하는 방법

디스크 I/O는 매우 느리기 때문에 압축/해제를 위한 CPU 연산 비용이 들더라도 디스크로 swap하는 것보다는 압축이 빠를 수 있다. 

압축된 페이지를 사용할 떄는 해당 데이터를 압축 해제하여 원래 페이지로 복원한 뒤 사용한다. 

## 커널 메모리 할당
커널 메모리는 일반적인 사용자 프로세스를 위한 메모리 할당과는 다른 방식을 사용한다. 
이유 : 단편화에 의한 낭비를 최소화해야하고, 물리적으로 연속적인 메모리가 있어야 하는 경우도 있다.

### 버디 시스템
물리적으로 연속된 페이지들로 이루어진 고정된 크기의 세그먼트로 메모리를 할당한다. 
요청된 크기를 수용할 수 있는 가장 작은 2^n 크기의 블록을 할당한다. 

빈 메모리는 처음에 개념적으로 크기가 2^N인 하나의 큰 공간으로 간주되며 메모리 요청이 들어오면 요청을 충족시키는 최적의 크기가 될 때까지 빈 공간을 $1/2$ 로 분할한다.

이 방식은 2의 거듭제곱 크기 만큼의 청크만 존재하기 때문에 내부 단편화가 흔하게 발생한다(단점). 버디 할당은 블럭이 해제될 때 그 장점이 빛을 발한다. ->  인접한 버디들이 손쉽게 하나의 큰 세그먼트로 합쳐질 수 있다. 

### 슬랩 할당
슬랩 할당기는 커널이 부팅될 때 커널 객체를 위한 여러 객체 캐시를 할당한다. 객체 캐시는 지정된 크기의 객체들로 구성된 빈 공간 리스트로 메모리 할당-해제 요청을 빠르게 서비스 하기 위해 사용한다. 기존에 할당된 캐시 공간이 부족하면 상위 메모리 할당기에 추가 슬랩을 요청하고 슬랩 내 객체들에 대한 참조가 사라지면 상위 메모리 할당기가 이 슬랩을 회수할 수 있다. 

빈 객체들을 사전에 초기화하여 유지한다는 점에서 개별 리스트 방식보다 우수하며 슬랩 할당기는 객체당 잦은 초기화와 반납을 피할 수 있어 오버헤드를 감소시킨다. 그리고 내부 단편화를 줄일 수 있다.  


## 기타 고려 사항
### prepaging
프로세스가 필요로 할 것으로 예상되는 페이지를 Page Fault가 발생하기 전에 미리 메모리에 적재하는 방식

Demand Paging에서 프로세스 시작이나 재시작 직후 Page Fault가 연속적으로 발생하는 문제를 줄이기 위해 사용한다. 하지만 미리 가져온 페이지가 실제로 사용되지 않으면 불필요한 I/O와 메모리 낭비가 발생한다.

-> Page Fault를 미리 방지하는 이득과 불필요한 페이지를 가져오는 비용 사이의 Trade-off가 존재한다.

### page size
페이지 크기는 가상 메모리의 성능과 메모리 사용량에 여러 영향을 준다.

- 페이지가 작으면
  - 내부 단편화(Internal Fragmentation)가 감소한다.
  - 필요한 데이터만 세밀하게 메모리에 올릴 수 있다.
  - 대신 페이지 수가 많아져 Page Table 크기가 증가한다.
- 페이지가 크면
  - Page Table 크기가 작아지고 한 번의 I/O로 많은 데이터를 가져올 수 있다.
  - TLB 하나의 엔트리가 커버하는 메모리 범위인 TLB Reach도 증가한다.
  - 사용하지 않는 데이터까지 메모리에 올라오면서 내부 단편화와 메모리 낭비가 증가할 수 있다.

> 작은 Page = 메모리를 세밀하게 사용 
> 큰 Page = 주소 변환 및 I/O 효율 증가


### TLB Reach
- TLB Reach : TLB가 Page Table을 다시 참조하지 않고 커버할 수 있는 메모리 영역의 크기

프로세스의 Working Set이 TLB Reach보다 크면 TLB에 모든 주소 변환 정보를 유지할 수 없어 TLB Miss가 자주 발생할 수 있다. 이를 해결하는 방법 중 하나가 페이지 크기를 증가시키는 것이다.

예를 들어 4KB 대신 2MB Huge Page를 사용하면 하나의 TLB Entry가 훨씬 넓은 메모리 영역을 담당할 수 있어 TLB Miss를 줄인는데 유리하다. 
다만 큰 페이지는 내부 단편화와 불필요한 메모리 사용을 증가시킬 수 있으므로 항상 유리한 것은 아니다.


### inverted page table
일반적인 Page Table은 프로세스의 Virtual Page마다 하나의 Page Table Entry를 가지므로 가상 주소 공간이 커지면 Page Table 자체가 많은 메모리를 사용할 수 있다.

Inverted Page Table은 반대로 물리 프레임마다 하나의 Entry를 유지하여 Page Table의 메모리 사용량을 줄인다.
-> 각 페이지 프레임에 어떤 가상 메모리 페이지가 저장되어 있는지의 정보만 유지하면 디므로 필요한 물리 메모리 양이 줄어든다. 만일 참조된 페이지가 메모리에 없으면 요구된 페이지가 디스크 어디에 있는지 알 수 없기 때문에 프로세스당 하나씩 확장도니 페이지 테이블을 유지해야한다. 

확장도니 페이블은 페이지 폴트시에만 참조되기 떄문에 빨리 읽어야 할 필요가 없다. 


### 프로그램 구조 
프로그램 역시 Locality를 잘 활용하도록 메모리 접근 패턴을 설계하는 것이 중요하다.

### I/O 상호 잠금과 페이지 잠금
I/O 작업에서는 장치가 사용자 메모리의 특정 페이지를 직접 읽거나 쓰는 경우가 있다. 이때 I/O가 끝나기 전에 해당 페이지가 Page Replacement의 victim으로 선택되면 문제가 발생할 수 있다.

```
1. Disk → Frame 10으로 I/O 시작

2. Page Replacement 발생
   Page A → Disk로 제거

3. Frame 10을 다른 Page B가 사용

4. 기존 I/O 완료
   Disk → Frame 10에 데이터 기록

5. Page B의 메모리가 엉뚱한 데이터로 덮어써짐
```

I/O Interlock은 I/O 작업이 진행되는 동안 관련 페이지가 교체되지 않도록 보장하는 메커니즘
```
I/O Interlock
"이 페이지 지금 I/O 중이니까 건드리지 마"
             ↓
       Page Locking
"그럼 이 페이지를 메모리에 고정해둘게"
             ↓
Page Replacement 대상에서 제외
```

#### Page Locking / Pinning
이를 막기 위해 I/O에 사용되는 페이지를 물리 메모리에 고정(Pin)한다. 페이지가 Lock된 동안에는 Page Replacement의 Victim으로 선택할 수 없다.

**그렇다고 모든 페이지를 Pinning하면 안 된다.**
Pinned Page는 Page Replacement 대상으로 사용할 수 없으므로 너무 많은 페이지를 고정하면 운영체제가 실제로 교체할 수 있는 프레임이 줄어든다.
결과적으로 메모리 부족이나 Page Fault 증가, 심하면 Thrashing에 가까운 상황을 악화시킬 수 있다.
따라서 일반적으로 필요한 페이지를 필요한 시간 동안만 Pinning하고 I/O가 완료되면 해제하는 것이 중요하다.
