# 동기화 도구

여러 프로세스나 스레드가 같은 데이터를 공유하면 실행 순서에 따라 결과가 달라질 수 있다. 동기화는 공유 데이터에 접근하는 순서를 조정하여 이런 문제를 막는 방법이다. 이번 장에서는 임계구역 문제를 해결하는 조건과 도구를 살펴보고, 이를 생산자-소비자 문제와 같은 고전적인 동기화 문제에 적용해 본다.

---

## 경쟁 상태와 임계구역 문제

### 경쟁 상태

경쟁 상태(race condition)는 여러 프로세스가 공유 데이터에 동시에 접근하여, 명령이 실행되는 순서에 따라 결과가 달라지는 상황을 말한다.

`count`가 5일 때 한 프로세스는 `count++`을, 다른 프로세스는 `count--`를 실행한다고 생각해 보자. 두 연산은 한 번에 끝나는 것처럼 보이지만 실제로는 값을 읽고, 계산하고, 저장하는 여러 명령으로 나뉜다.

```c
// count++
register1 = count;
register1 = register1 + 1;
count = register1;

// count--
register2 = count;
register2 = register2 - 1;
count = register2;
```

두 연산을 차례대로 끝냈다면 결과는 다시 5가 된다. 그러나 다음처럼 명령이 섞여 실행될 수 있다.

1. 증가 연산이 `count`의 값 5를 읽는다.
2. 감소 연산도 `count`의 값 5를 읽는다.
3. 감소 연산이 계산한 4를 `count`에 저장한다.
4. 증가 연산이 계산한 6을 `count`에 저장한다.

마지막 값은 6이 된다. 어느 연산이 나중에 저장하느냐에 따라 결과가 4나 6이 될 수 있다. 공유 데이터의 최종 상태가 실행 시점에 좌우되기 때문에 결과를 예측할 수 없다.

### 임계구역

공유 데이터를 읽거나 변경하는 코드 영역을 임계구역(critical section)이라고 한다. 한 프로세스가 임계구역을 실행하는 동안 다른 프로세스가 같은 임계구역에 들어오지 못하게 해야 경쟁 상태를 막을 수 있다.

프로세스의 코드는 임계구역을 기준으로 다음 네 영역으로 나눌 수 있다.

```c
do {
    // 진입 구역: 임계구역에 들어갈 권한을 요청한다.

    // 임계구역: 공유 데이터에 접근한다.

    // 퇴장 구역: 사용하던 권한을 반납한다.

    // 나머지 구역: 공유 데이터와 관계없는 작업을 수행한다.
} while (true);
```

임계구역 문제는 진입 구역과 퇴장 구역을 어떻게 구성해야 공유 데이터를 안전하게 다룰 수 있는지에 관한 문제다.

### 임계구역 문제의 세 가지 조건

임계구역 문제의 해결안은 다음 조건을 만족해야 한다.

1. **상호 배제(mutual exclusion)**
   - 한 프로세스가 임계구역을 실행하고 있다면 다른 프로세스는 그 임계구역에 들어갈 수 없어야 한다.
2. **진행(progress)**
   - 임계구역이 비어 있고 진입하려는 프로세스가 있다면, 다음에 들어갈 프로세스를 정하는 과정이 무한히 미뤄져서는 안 된다.
   - 임계구역에 들어갈 수 있는데도 모두가 기다리는 교착 상태를 막기 위한 조건이다.
3. **한정 대기(bounded waiting)**
   - 한 프로세스가 진입을 요청한 뒤 다른 프로세스들이 먼저 들어갈 수 있는 횟수에는 한계가 있어야 한다.
   - 특정 프로세스만 계속 선택받지 못하는 기아 상태를 막기 위한 조건이다.

상호 배제만 만족한다고 해서 나머지 두 조건까지 자연스럽게 해결되는 것은 아니다. 공유 데이터는 보호하면서도 각 프로세스가 언젠가는 실행될 수 있도록 함께 고려해야 한다.

## Peterson의 해결안

Peterson의 해결안은 두 프로세스의 임계구역 문제를 소프트웨어만으로 해결하는 알고리즘이다. 프로세스가 임계구역에 들어가고 싶은지를 나타내는 `flag` 배열과, 상대에게 차례를 양보하는 `turn` 변수를 사용한다.

프로세스 `Pi`에서 실행하는 코드는 다음과 같다. `j`는 다른 프로세스의 번호다.

```c
do {
    flag[i] = true;
    turn = j;

    while (flag[j] && turn == j)
        ;

    // 임계구역

    flag[i] = false;

    // 나머지 구역
} while (true);
```

실행 흐름은 다음과 같다.

1. `Pi`는 `flag[i]`를 `true`로 바꾸어 임계구역에 들어갈 뜻을 밝힌다.
2. `turn`을 `j`로 바꾸어 두 프로세스가 동시에 진입을 원할 때 상대에게 우선권을 준다.
3. 상대도 진입을 원하고 상대 차례라면 `while`에서 기다린다.
4. 상대가 진입을 원하지 않거나 자신의 차례가 되면 임계구역에 들어간다.
5. 임계구역을 나오면서 `flag[i]`를 `false`로 바꾼다.

두 프로세스가 동시에 진입을 원해도 `turn`은 한 값만 가질 수 있으므로 둘 중 하나만 대기를 벗어난다. 임계구역을 나온 프로세스는 자신의 `flag`를 내리기 때문에 기다리던 프로세스도 이어서 진입할 수 있다. 이론적으로 상호 배제, 진행, 한정 대기를 모두 만족한다.

다만 이 알고리즘은 메모리 읽기와 쓰기가 코드에 적힌 순서대로 보인다고 가정한다. 현대 시스템에서는 컴파일러나 프로세서가 서로 의존하지 않는 명령의 순서를 바꿀 수 있다. `flag`와 `turn`의 변경 순서가 재배치되면 알고리즘이 기대한 동작을 보장하기 어렵다. 실제 프로그램에서는 하드웨어가 제공하는 원자적 명령과 동기화 도구를 사용한다.

## 하드웨어 동기화 지원

### 메모리 장벽

메모리 장벽(memory barrier)은 장벽 앞의 메모리 읽기와 쓰기가 완료된 뒤 장벽 뒤의 연산이 실행되도록 순서를 제한하는 명령이다. 한 프로세서가 변경한 값이 다른 프로세서에도 보이도록 하여 명령 재배치와 메모리 가시성 문제를 다룬다.

Peterson의 해결안처럼 여러 공유 변수의 읽기와 쓰기 순서가 중요한 알고리즘은 이런 보장이 없다면 코드에 적힌 순서와 실제로 관찰되는 순서가 달라질 수 있다.

### 검사 후 지정(Test-and-Set)

현대 시스템은 값을 검사하고 변경하는 과정을 한 번에 수행하는 하드웨어 명령을 제공한다. 원자적 연산(atomic operation)은 중간에 끊어지지 않고 하나의 단위로 실행되는 연산이다.

`test_and_set()`은 대상의 기존 값을 반환하면서 그 값을 `true`로 바꾼다. 다음 함수 전체가 원자적으로 실행된다고 가정한다.

```c
boolean test_and_set(boolean *target) {
    boolean old = *target;
    *target = true;
    return old;
}
```

이를 이용하면 간단한 락을 만들 수 있다.

```c
do {
    while (test_and_set(&lock))
        ;

    // 임계구역

    lock = false;

    // 나머지 구역
} while (true);
```

처음 `lock`은 `false`다. 한 프로세스만 기존 값으로 `false`를 받아 반복문을 빠져나가고, 나머지는 `true`를 받으며 기다린다. 임계구역을 나온 프로세스가 `lock`을 `false`로 바꾸면 다음 프로세스가 진입할 수 있다.

이 방법은 상호 배제를 보장하지만 기다리는 동안 계속 락을 검사한다. 또 다음에 진입할 프로세스를 정하는 규칙이 없으므로 한정 대기를 보장하지 않는다.

### 비교 후 교환(Compare-and-Swap)과 원자적 변수

비교 후 교환(compare-and-swap)은 메모리의 값이 예상한 값과 같을 때만 새 값으로 바꾸며, 비교와 변경을 하나의 원자적 연산으로 수행한다. 값을 검사한 뒤 다른 프로세스가 끼어들어 값을 바꾸는 틈이 없다는 점이 핵심이다.

이 명령을 바탕으로 정수나 논리값을 원자적으로 갱신하는 원자적 변수를 만들 수 있다. 하나의 공유 변수에 대한 증가나 감소처럼 단순한 연산을 안전하게 처리하는 데 유용하다. 여러 변수와 여러 단계의 연산을 하나의 규칙으로 묶어야 한다면 원자적 변수 하나만으로는 충분하지 않으며, 임계구역 전체를 보호하는 동기화 도구가 필요하다.

## 뮤텍스 락

뮤텍스(mutex)는 상호 배제를 제공하는 가장 단순한 동기화 도구다. 프로세스는 임계구역에 들어가기 전에 `acquire()`로 락을 얻고, 나온 뒤 `release()`로 반납한다. 락을 확인하고 변경하는 동작 자체도 원자적으로 실행되어야 한다.

```c
do {
    acquire(lock);

    // 임계구역

    release(lock);

    // 나머지 구역
} while (true);
```

락이 풀릴 때까지 반복해서 상태를 확인하는 방식을 바쁜 대기(busy waiting)라고 하며, 이런 락을 스핀락(spinlock)이라고 한다. 기다리는 동안 CPU를 계속 사용한다는 단점이 있지만, 락을 짧게 보유하는 멀티프로세서 환경에서는 문맥 교환 없이 바로 실행을 이어갈 수 있다.

뮤텍스는 임계구역에 한 번에 한 프로세스만 들어가게 하지만, 락을 얻는 순서까지 자동으로 공정하게 정해 주지는 않는다. 사용 순서가 잘못되면 교착이나 기아가 생길 수 있다.

## 세마포어

세마포어(semaphore)는 정수 변수 `S`와 원자적으로 실행되는 `wait()`와 `signal()` 연산으로 구성된다.

```c
wait(S) {
    while (S <= 0)
        ;
    S--;
}

signal(S) {
    S++;
}
```

`wait()`는 사용할 수 있는 자원이 생길 때까지 기다린 뒤 자원의 수를 하나 줄이고, `signal()`은 사용을 마친 자원을 하나 돌려놓는다. 위 코드는 동작을 보여 주기 위한 형태다. 실제 구현에서는 기다리는 프로세스를 대기 큐에 넣고 잠들게 한 뒤, `signal()`이 호출되면 하나를 준비 큐로 옮겨 바쁜 대기를 줄일 수 있다.

세마포어는 값의 범위에 따라 두 종류로 나뉜다.

- 이진 세마포어는 0과 1만 사용하며 뮤텍스와 비슷하게 동작한다.
- 카운팅 세마포어는 여러 인스턴스를 가진 자원의 가용 개수를 관리한다.

세마포어는 상호 배제뿐 아니라 실행 순서를 맞추는 데에도 사용할 수 있다. `P1`의 작업 `S1`이 끝난 뒤 `P2`의 작업 `S2`를 실행해야 한다면 세마포어 `sync`를 0으로 초기화한다.

```c
// P1
S1;
signal(sync);

// P2
wait(sync);
S2;
```

`P2`가 먼저 실행되어도 `sync`가 0이므로 기다린다. `P1`이 `S1`을 끝내고 신호를 보낸 뒤에야 `S2`가 실행된다.

`wait()`와 `signal()`의 순서를 잘못 적거나 연산을 빠뜨리면 상호 배제가 깨지거나 모든 프로세스가 서로를 기다릴 수 있다. 세마포어는 강력하지만 올바른 사용 책임이 프로그래머에게 있다.

## 모니터

모니터(monitor)는 공유 데이터와 그 데이터를 다루는 연산을 하나로 묶은 추상 자료형이다. 모니터 내부에서는 한 번에 하나의 프로세스만 활성화되므로 프로그래머가 모든 연산 앞뒤에 직접 락을 배치하지 않아도 상호 배제가 보장된다.

모니터 안에서 특정 조건이 충족되기를 기다릴 때는 조건 변수(condition variable)를 사용한다.

- `x.wait()`를 호출한 프로세스는 실행을 멈추고 `x`의 대기 큐로 이동한다.
- `x.signal()`은 `x`에서 기다리는 프로세스 하나를 깨운다. 기다리는 프로세스가 없다면 아무 일도 하지 않는다.

`signal()`을 호출한 프로세스와 깨어난 프로세스가 동시에 모니터 안에서 실행될 수는 없다. 그래서 다음 두 방식 중 하나로 실행 순서를 정한다.

- 신호 후 대기 방식은 신호를 보낸 프로세스가 기다리고, 깨어난 프로세스가 먼저 실행된다.
- 신호 후 계속 방식은 신호를 보낸 프로세스가 모니터를 나갈 때까지 실행을 이어간 뒤, 깨어난 프로세스가 실행된다.

모니터는 세마포어보다 동기화 규칙을 자료형 안에 모아 표현하기 쉽다. 다만 모니터를 사용한다고 교착이나 기아까지 자동으로 사라지는 것은 아니다. 조건과 실행 순서를 잘못 설계하면 프로세스가 계속 기다릴 수 있다.

## 생산자-소비자 문제

생산자-소비자 문제에서는 생산자가 만든 항목을 유한한 크기의 버퍼에 넣고 소비자가 꺼낸다. 생산자는 빈 칸이 없을 때 기다려야 하고, 소비자는 꺼낼 항목이 없을 때 기다려야 한다. 두 프로세스가 버퍼를 동시에 변경하지 못하게 하는 상호 배제도 필요하다.

크기가 `n`인 버퍼에 다음 세마포어를 사용한다.

```c
semaphore mutex = 1; // 버퍼에 한 번에 하나만 접근한다.
semaphore empty = n; // 비어 있는 칸의 수
semaphore full = 0;  // 항목이 들어 있는 칸의 수
```

생산자는 다음 순서로 동작한다.

```c
do {
    // next_produced에 항목을 생산한다.

    wait(empty);
    wait(mutex);

    // next_produced를 버퍼에 넣는다.

    signal(mutex);
    signal(full);
} while (true);
```

`wait(empty)`는 빈 칸 하나를 예약한다. 그 뒤 `wait(mutex)`로 버퍼를 잠그고 항목을 넣는다. 작업이 끝나면 락을 반납하고, `full`을 증가시켜 소비자에게 꺼낼 항목이 생겼음을 알린다. 버퍼가 모두 찰 때까지 기다리는 것이 아니라 항목을 하나 넣을 때마다 신호를 보낸다.

소비자는 반대 순서로 동작한다.

```c
do {
    wait(full);
    wait(mutex);

    // 버퍼에서 항목을 꺼내 next_consumed에 저장한다.

    signal(mutex);
    signal(empty);

    // next_consumed의 항목을 소비한다.
} while (true);
```

`empty`와 `full`은 버퍼의 상태를 세고, `mutex`는 버퍼를 변경하는 임계구역을 보호한다. 세 변수의 역할을 나누었기 때문에 생산자와 소비자는 서로의 작업 시점을 맞추면서도 버퍼를 안전하게 공유할 수 있다.

## 독자-저자 문제

독자-저자 문제에서는 여러 프로세스가 하나의 데이터를 읽거나 쓴다. 여러 독자가 동시에 읽는 것은 데이터의 값을 바꾸지 않으므로 허용할 수 있다. 반면 저자가 쓰는 동안에는 다른 저자뿐 아니라 독자도 데이터에 접근하면 안 된다.

첫 번째 독자-저자 문제는 이미 읽고 있는 독자가 있다면 새 독자도 기다리지 않고 들어갈 수 있도록 한다. 다음 공유 변수를 사용한다.

```c
semaphore rw_mutex = 1; // 독자 집단과 저자의 공유 데이터 접근을 제어한다.
semaphore mutex = 1;    // read_count를 보호한다.
int read_count = 0;
```

저자는 공유 데이터 전체를 독점한다.

```c
do {
    wait(rw_mutex);

    // 공유 데이터에 쓴다.

    signal(rw_mutex);
} while (true);
```

독자는 현재 읽고 있는 프로세스의 수를 함께 관리한다.

```c
do {
    wait(mutex);
    read_count++;
    if (read_count == 1)
        wait(rw_mutex);
    signal(mutex);

    // 공유 데이터를 읽는다.

    wait(mutex);
    read_count--;
    if (read_count == 0)
        signal(rw_mutex);
    signal(mutex);
} while (true);
```

첫 번째 독자가 `rw_mutex`를 얻어 저자의 접근을 막고, 마지막 독자가 나갈 때 이를 반납한다. 그 사이에 들어온 독자들은 함께 데이터를 읽을 수 있다. `read_count`를 변경하는 연산도 공유 데이터에 대한 접근이므로 별도의 `mutex`로 보호한다.

이 방식에서는 독자가 계속 들어오면 `read_count`가 0이 되지 않아 저자가 오랫동안 기다릴 수 있다. 두 번째 독자-저자 문제는 저자가 기다리기 시작하면 새 독자의 진입을 막아 저자에게 우선권을 준다. 이 경우에는 반대로 독자가 기아 상태에 빠질 수 있다. 읽기 모드에서는 여러 프로세스의 접근을 허용하고 쓰기 모드에서는 하나만 허용하는 독자-저자 락을 사용할 수도 있다.

## 식사하는 철학자 문제

다섯 철학자가 원형 식탁에 앉아 생각하거나 식사한다고 가정한다. 철학자 사이에는 젓가락이 하나씩 놓여 있으며, 각 철학자는 양옆의 젓가락 두 개를 모두 잡아야 식사할 수 있다. 이 문제는 여러 프로세스가 여러 자원을 동시에 얻으려 할 때 생기는 동기화 문제를 보여 준다.

각 젓가락을 값이 1인 세마포어로 나타내면 한 젓가락을 두 철학자가 동시에 사용하는 일은 막을 수 있다.

```c
do {
    wait(chopstick[i]);
    wait(chopstick[(i + 1) % 5]);

    // 식사한다.

    signal(chopstick[i]);
    signal(chopstick[(i + 1) % 5]);

    // 생각한다.
} while (true);
```

그러나 다섯 철학자가 동시에 왼쪽 젓가락을 잡으면 모두 오른쪽 젓가락을 기다리게 된다. 각자 자원 하나를 가진 채 이웃이 가진 자원을 기다리므로 아무도 진행하지 못하는 교착 상태가 된다. 세마포어로 젓가락의 상호 배제를 지킨 것만으로는 충분하지 않다.

교착을 피하는 방법은 다음과 같다.

- 식탁에 동시에 앉을 수 있는 철학자를 네 명으로 제한한다.
- 양쪽 젓가락을 모두 사용할 수 있을 때만 잡게 한다.
- 홀수 번호 철학자와 짝수 번호 철학자가 젓가락을 잡는 순서를 반대로 정한다.

양쪽 젓가락이 모두 비었을 때만 식사를 시작하는 규칙은 모니터로 표현할 수 있다. 철학자의 상태를 `THINKING`, `HUNGRY`, `EATING`으로 나누고, 양옆 철학자가 식사 중이 아닐 때만 `HUNGRY`에서 `EATING`으로 바꾼다.

```c
test(i) {
    if (state[i] == HUNGRY &&
        state[left(i)] != EATING &&
        state[right(i)] != EATING) {
        state[i] = EATING;
        self[i].signal();
    }
}

pickup(i) {
    state[i] = HUNGRY;
    test(i);
    if (state[i] != EATING)
        self[i].wait();
}

putdown(i) {
    state[i] = THINKING;
    test(left(i));
    test(right(i));
}
```

`pickup()`은 양쪽 철학자의 상태를 검사한 뒤 식사할 수 없으면 자신의 조건 변수에서 기다린다. `putdown()`은 젓가락을 내려놓은 뒤 양옆 철학자가 식사할 수 있는지 확인하고 깨운다. 이 방법은 서로 이웃한 철학자가 동시에 식사하지 못하게 하고 교착을 피한다. 다만 특정 철학자가 계속 선택받지 못할 가능성까지 없애지는 못하므로 기아 문제는 별도로 고려해야 한다.
